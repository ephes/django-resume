Clone the repository
--------------------

Get the source code using the following command:

.. code-block:: sh

    $ git clone https://github.com/ephes/django-resume.git

Switch to the django-resume directory:

.. code-block:: sh

    $ cd django-resume

Install the pre-commit hooks
----------------------------

.. code-block:: sh

    $ uvx run pre-commit install

Install the Package using uv
----------------------------

.. code-block:: sh

    $ uv sync --dev

Repository Checks
-----------------

Show the available ``just`` commands with:

.. code-block:: sh

    $ just

Run the full local validation suite with:

.. code-block:: sh

    $ just check

GitHub Actions (``.github/workflows/ci.yml``) runs the same checks in
check-only mode (``ruff check``, ``ruff format --check``, mypy, pytest with
coverage) plus ``npx vitest run`` on every push and pull request. The
synthetic Playwright editor suite also runs in CI; the live-server Playwright
suite is separate. Run the editor suite locally with::

    uv run playwright install chromium
    uv run pytest -q e2e_tests/editable_form_test.py

It uses inline synthetic HTML and files without accounts, a database or a
server. It checks native click/Enter/``requestSubmit()`` submission and actual
``FormData`` file contents after successful and rejected drops. Vitest covers
controlled reader completion order, failures, cancellation and reconnects.

Browser mutation CSRF regressions
---------------------------------

Run the real-middleware owner-session regressions with::

    uv run pytest -q tests/browser_mutation_csrf_test.py

They cover file preview/confirmation, URL import, whole-resume DELETE, and
simple, flat and list-item inline edits. Valid preview confirmations and editor
revisions are supplied even when CSRF proof is rejected. Missing/mismatched
proof and foreign origins must reject before URL fetches, import preparation,
database writes or avatar storage. Same-origin controls exercise the real saves
with synthetic documents and in-memory images; no external service is used.

Rendered editor and import oracles
----------------------------------

``tests/plugin_stale_edit_test.py`` selects each rendered form by its HTMX
POST URL and submits its successful input controls, including hidden revision
and item ID fields. The existing save/stale/target-isolation checks now cover
admin forms and plain, editorial and headwind inline forms using HTML rather
than form context. Validation-error forms are parsed and resubmitted too. The
fixture reader handles input controls only and fails explicitly if these forms
acquire select/textarea controls, which would require extending the reader.

``tests/json_resume_import_preview_test.py`` uses handwritten expected plugin
fields, omission reasons, loss notes and export documents for an invented
resume. It covers portable documents, envelope restoration and ignoring an
envelope, independently of the shared preview/create mapper. Run both with::

    uv run pytest -q tests/plugin_stale_edit_test.py tests/json_resume_import_preview_test.py

Resume language contexts
------------------------

``with_resume_language`` supports sync and async inline views. Each async
request keeps its own resume language across awaits and restores its caller's
language on success, exceptions and cancellation. Deferred template responses
render later in the resume language; a failed render keeps its wrapper for retry
only while the response remains unrendered. Successful post-render callbacks
can pickle the response or replace it without retaining the local wrapper.

The language suite uses real decorated views, synthetic database records and
event rendezvous points in one event loop, plus a real lazy template that fails
once before succeeding. Run it with::

    uv run pytest -q tests/pages/resume_language_test.py

Failure cleanup
---------------

Plugin command ownership regressions use spawned processes on every platform,
synthetic plugin bundles and a temporary SQLite database. They cover competing
create/create and create/remove writers, independent plugins, rollback and
backup cleanup under warnings-as-errors. Run them with::

    uv run pytest -q tests/plugin_file_ownership_test.py tests/management_commands_test.py

Image forms compensate failed mutations by deleting only their newly stored
uploads. Every owned object is attempted. A failed delete keeps the object in
``form.new_image_uploads`` for retry and emits an ERROR through
``django_resume.images`` with ``object_id`` (the first 16 hexadecimal characters
of SHA-256 of the UTF-8 storage name) and ``exception_class`` (at most 80
characters). Storage names, exception messages and tracebacks are omitted from
these cleanup events. To investigate orphans, compare this identifier with hashes
of candidate objects in the configured storage and confirm that an object is
unreferenced before removing it. Existing referenced images are never cleanup
targets. During an active exception, cleanup preserves that original failure;
standalone ``cleanup_new_image_uploads()`` still raises the first deletion error
after attempting every object.

Theme rendering and npm commands own their child process from successful spawn.
Any abnormal exit, including ``KeyboardInterrupt`` or partial reader-thread
startup, attempts process-group termination, bounded reaping, stream closure and
bounded joins of readers that started. Secondary cleanup errors do not replace
the initiating exception. POSIX uses the child's new process group; Windows
retains the existing direct-child termination behavior. Timeout and captured
output limits still apply. Regressions use synthetic storage and fake processes
and threads so interruption checks do not depend on operating-system signals.

Python dependency advisory audit
--------------------------------

Run the same network-dependent advisory gate used by CI with:

.. code-block:: sh

    $ just audit

The command uses pinned ``pip-audit==2.10.1`` against ``uv export --locked``
requirements for all dependency groups (runtime, dev, e2e and postgres).
Only pip-audit's top-level version is pinned; its isolated tool dependencies
are resolved separately from PyPI and are not locked by this repository.
It rejects stale locks even when ``UV_FROZEN=1`` is set for CI installs.
Export and audit failures propagate to CI. The fully pinned registry graph is
audited without installing it or resolving newer dependencies.

The export explicitly excludes ``django-resume`` (the project under test) and
``resume-entrypoint-demo`` (the editable local fixture under
``example/resume_entrypoint_demo``, which has no registry version). Their code
is covered by package/entrypoint tests, not by the registry advisory service.
The audit evaluates requirement markers for the running interpreter/platform:
CI covers Python 3.14 on Linux, not every Python/platform branch in the lock.
Run the command in each additional supported environment when checking its
marker-specific graph. No advisories are ignored.

The setuptools 84.1.0 refresh addresses
`GHSA-xmj3-9gf7-h52w <https://github.com/pypa/setuptools/security/advisories/GHSA-xmj3-9gf7-h52w>`_,
which affects Windows legacy ``Wheel.install_as_egg`` handling of crafted
``namespace_packages.txt`` paths. This is development/build tooling exposure;
it does not establish a remotely exploitable resume endpoint. Refresh those
environments with ``uv sync --frozen --dev``; no service deploy is required.

Line Count Overview
-------------------

Show a colorized repository line-count summary with language totals, a high-level
``src`` vs ``tests`` overview, and a directory breakdown:

.. code-block:: sh

    $ just loc

The helper uses ``cloc`` when available, with a 60-second timeout for each
of its two invocations (summary and file details). Timeout or startup failure
prints a diagnostic to stderr and exits with status 1, without a partial report.
Other cloc failures retain cloc's nonzero exit status. If ``cloc`` is not found
before execution, the existing Python fallback counts lines and exits with
status 0; it does not replace a failed cloc run.

End to End Tests
----------------

The browser tests in ``e2e_tests/`` use Playwright against pytest-django's
live server, with the example project's settings and a throwaway test
database (``e2e_tests.settings``). They do not need a running development
server or a prepared user: each test creates the users and resumes it needs,
and the database is emptied after every test. Uploaded files go to
``e2e_tests/media/``.

Install the e2e dependency group (the entry-point page tests need it) and a
browser:

.. code-block:: sh

    $ uv sync --group e2e
    $ uv run playwright install chromium

Run the e2e tests with:

.. code-block:: sh

    $ uv run pytest --ds=e2e_tests.settings e2e_tests

Run them in head-full mode:

.. code-block:: sh

    $ uv run pytest --ds=e2e_tests.settings e2e_tests --headed --slowmo 1000

If another project installs Playwright browsers at the same time, the shared
browser cache can be locked. Install into a project-local path instead and
pass the same ``PLAYWRIGHT_BROWSERS_PATH`` when running the tests.


Build the Documentation
-----------------------

The documentation is built using Sphinx with the furo theme.
To build the documentation, run the following commands:

.. code-block:: sh

    $ make -C docs clean
    $ make -C docs html

The documentation will be available in the `docs/_build/html` directory:

.. code-block:: sh

    $ open docs/_build/html/index.html

Serve the built documentation locally with:

.. code-block:: sh

    $ just docs-serve

Pass a custom port as the first argument when needed:

.. code-block:: sh

    $ just docs-serve 9000

Update Javascript Dependencies
------------------------------

Check with `npm outdated` if there are any outdated dependencies. If there are, update them:

.. code-block:: sh

    $ npm update

Release Process
---------------

Use this checklist when preparing a package release. The project currently
releases from ``main`` and uses plain version-number git tags, for example
``0.1.14``.

1. Start from a clean worktree:

   .. code-block:: sh

       $ git status --short

2. Choose the next version number.

   Use a patch release for small fixes. Use a minor release when the
   ``Unreleased`` changelog contains breaking changes or larger feature work.

3. Update the version number in:

   - ``pyproject.toml``
   - ``docs/conf.py``

4. Update ``docs/changelog.txt``:

   - Move the current ``Unreleased`` entries under a new
     ``X.Y.Z - YYYY-MM-DD`` heading, and match the underline length to the
     heading text.
   - Leave a fresh ``Unreleased`` section above the new release entry.
     The fresh section should look like::

       Unreleased
       ----------

   - Keep breaking changes, features, and fixes grouped under the release
     where applicable.

5. Run the release validation gates:

   .. code-block:: sh

       $ just check
       $ make -C docs html

6. Clean old package artifacts and build the package.

   .. admonition:: wheel/sdist issues

       ``uv build`` will build both a wheel and a sdist. But the wheel
       will be empty. To build a wheel with the correct content, you
       need to run ``uv build --wheel`` and ``uv build --sdist`` separately.

   .. code-block:: sh

       $ rm -rf dist/
       $ uv build --wheel
       $ uv build --sdist

7. Validate the package artifacts:

   .. code-block:: sh

       $ uvx twine check dist/django_resume-*.whl dist/django_resume-*.tar.gz

8. Commit the release prep changes:

   .. code-block:: sh

       $ git add pyproject.toml docs/conf.py docs/changelog.txt
       $ git commit -m "Release X.Y.Z"

9. Create an annotated release tag:

   Older releases used lightweight tags. Use annotated tags for new releases so
   the release metadata is explicit.

   .. code-block:: sh

       $ git tag -a X.Y.Z -m "Release version X.Y.Z"

10. Publish the package to ``pypi.org``:

    .. code-block:: sh

        $ uv publish --token your_token

11. Push the release commit and tag:

    .. code-block:: sh

        $ git push
        $ git push origin X.Y.Z

12. Create a GitHub release from the pushed tag and upload the checked package
    artifacts. Use the release section from ``docs/changelog.txt`` as the
    release notes, for example via a temporary ``release-notes.md`` file:

    .. code-block:: sh

        $ gh release create X.Y.Z \
              dist/django_resume-X.Y.Z-py3-none-any.whl \
              dist/django_resume-X.Y.Z.tar.gz \
              --verify-tag \
              --title "X.Y.Z" \
              --notes-file release-notes.md

Publishing, pushing, and creating GitHub releases are maintainer actions.
Agents preparing a release should stop after validation and artifact
generation, then report the remaining ``uv publish``, ``git push``, and
``gh release create`` commands for the maintainer to run.


Theme selection concurrency
---------------------------

``just check`` includes SQLite conflict and stale-instance regressions. CI also
runs the selection suite against an ephemeral PostgreSQL 17 service, exercising
a real row-lock wait while another integration writer commits. To run it with a
local disposable database named ``resume_test`` and the synthetic credentials
in ``tests/postgres_settings.py``::

    uv sync --group postgres
    DJANGO_SETTINGS_MODULE=tests.postgres_settings uv run --group postgres pytest -v tests/theme_selection_concurrency_test.py tests/resume_delete_authority_test.py

The deletion suite holds an uncommitted owner transfer on a second connection:
the current-owner DELETE lookup must wait, then deny the former owner without
deleting the transferred resume. The fixtures contain only synthetic data;
no production database is used.

Routed editor transactions
--------------------------

The PostgreSQL CI job also runs ``tests/plugin_resume_mutation_test.py`` and
``tests/plugin_stale_edit_test.py``. Two separate synthetic databases verify
alias-specific rollback and real competing editor row locks. The same editor
GET/POST regressions run on SQLite in ``just check``. Locally, with the
PostgreSQL 17 fixture databases from ``tests/postgres_settings.py`` available,
run::

    uv sync --frozen --group postgres
    DJANGO_SETTINGS_MODULE=tests.postgres_settings uv run --group postgres pytest -q tests/plugin_resume_mutation_test.py tests/plugin_stale_edit_test.py

Handwriting runtime regression tests
------------------------------------

``npx vitest run`` executes the shipped handwriting JavaScript and CSS in an
isolated jsdom document with synthetic stroke measurements and an observer.
Fake time covers stale callbacks, replay/observer overlap, cooldown boundaries,
lead/rail ordering, removed targets and failure recovery. No server or personal
data is needed. Pixel-level SVG mask coverage (including repeated horizontal and
vertical labels) remains a Chromium check::

    uv run pytest --ds=e2e_tests.settings e2e_tests/editorial_handwriting_test.py
