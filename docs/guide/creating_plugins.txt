==========================
Tutorial: Creating Plugins
==========================

.. admonition:: Choose your tutorial

   django-resume supports two types of plugins. Choose the tutorial that matches your needs:

   - **Simple Plugins**: Single-form plugins like "About", "Motto", or "Contact Info"
   - **List Plugins**: Multi-item plugins like "Projects", "Certifications", or "Jobs"

Overview
========

Plugins in django-resume are Python classes that define how specific sections
of a resume are displayed and edited. Each plugin handles its own data,
provides forms for editing, and renders content using templates.

Custom plugins are filesystem-based: you add Python modules to your project,
store templates on disk, and register the plugin classes from Python code.
Database-backed plugins are no longer supported.

Plugin Types
============

django-resume provides two base plugin types:

**SimplePlugin**
   For plugins with a single form and straightforward data structure.
   
   Examples: About section, personal motto, contact information, availability status.
   
   **When to use**: When you need to store and display a single piece of content
   that doesn't need to be broken into multiple items.

**ListPlugin**
   For plugins that manage collections of related items.
   
   Examples: Work experience, projects, certifications, education, skills.
   
   **When to use**: When users need to add, edit, and manage multiple related items
   with individual forms and ordering.

Quick Start Recommendations
===========================

**For beginners or simple content**:
   Start with :doc:`creating_simple_plugins` to learn the fundamentals.

**For experienced developers**:
   Jump to :doc:`creating_list_plugins` if you need to manage multiple items.

**Not sure which to choose?**
   Ask yourself: "Will users want to add multiple instances of this content?"
   
   - **Yes** → Use List Plugin
   - **No** → Use Simple Plugin

Supported Custom Plugin Workflow
================================

Custom plugins are added in three parts:

1. Write the plugin class in your Django project.
2. Add the plugin templates under ``templates/django_resume/plugins/...``.
3. Register the plugin class from your app's Python code, usually in
   ``AppConfig.ready()``.

This keeps plugin behavior explicit and version-controlled alongside the rest
of your project code.

Removing filesystem plugins
---------------------------

Run ``python manage.py remove_plugin_by_name NAME`` from your project's root
to remove ``core/plugins/NAME.py``, the plain content/form templates under
``templates/django_resume/plugins/NAME/plain/``, and that plugin's stored data
from every resume. Missing files are allowed. All three paths are validated
before any changes; paths escaping their expected tree or resolving to the
same file are rejected.

The command records a persistent removal intent and creates sibling ``.FILENAME.backup-*`` copies before removing
files and uses a database transaction on the Resume write alias selected once
by Django's router. The data manager is bound to that same alias; a read replica
or ``default`` is not accessed when writes route elsewhere. File restoration
happens outside the transaction, after a rollback before commit. Resume rows are
locked where supported and checked against their original JSON data before
updating. A concurrent SQLite edit can abort removal with a database conflict;
retry the whole command after that writer finishes. An ordinary file or
database failure before commit rolls back the data change and restores the
files. Ctrl+C before commit also triggers restoration. A failure or interruption
while committing the selected database (for example a dropped connection during
``COMMIT``) cannot prove a rollback: the command reports ``database outcome
uncertain after commit attempt``, leaves the files removed and retains the
removal intent and backups for the explicit recovery below. Cooperating create/remove commands take native ``filelock`` locks
on each resolved target, in sorted order, before backup and hold them through
the database transaction and any rollback. Waiting has a total 10-second budget;
a busy writer raises ``CommandError`` and can be retried. Unrelated plugin
targets remain independent. Lock names are SHA-256 hashes of normalized resolved
target paths in a private per-account directory under Python's OS temporary
directory (``django-resume-plugin-locks-ACCOUNT/*.lock``). On POSIX this directory
must be owned by the current uid with no group/other permissions; symlinks and
non-directories are rejected. Cooperating writers must run as the same account,
share that directory (including the same ``TMPDIR`` configuration), and use the
same canonical path spelling and mount. Separate temp/container namespaces or
alternate case spellings on case-insensitive filesystems are outside this lock
contract. No output directories are created just to remove absent files.

Do not manually delete active lock files; ``filelock`` owns their lifecycle.
Locks are released when their process exits, even if files remain. A busy
writer can be retried after it finishes. If the lock directory is unsafe or
inaccessible, stop all cooperating writers and configure the same private
``TMPDIR`` for every invocation before retrying; do not remove another user's
lock directory or switch namespaces while a writer is active.

This is not a transaction across the filesystem and database. Process
termination leaves an unresolved removal intent and retained backups, including
when the database commit already happened. See the recovery procedure below.
Stop unrelated editors and keep a database backup. If ordinary restoration
fails, the error lists the intent and retained backup locations; use explicit
recovery before retrying. A backup cleanup warning after success
means the operation completed but the named leftover backup needs removal.
Cleanup logs a bounded warning through
``django_resume.management.commands._file_rollback`` naming leftover paths;
even strict Python warning filters or a failing logging handler cannot replace
the primary error or turn completed publication into failure. Failed
restoration retains the recovery copy.

Installing filesystem plugin bundles
------------------------------------

``python manage.py create_plugin_from_stdin < bundle.txt`` intentionally
replaces existing plugin files. The bundle begins with ``===NAME===`` and must
contain exactly one section for each of ``===NAME.py===``,
``===django_resume/plugins/NAME/plain/content.html===``, and
``===django_resume/plugins/NAME/plain/form.html===``. Names use lowercase
letters, numbers and underscores, starting with a letter. Missing, duplicate,
unknown or malformed sections raise ``CommandError`` before output files are
opened. Generation and stdin installation preserve literal ``---`` in form
text, comments, attributes and scripts. A legacy end-of-response marker is
recognized only when ``---`` occupies the final line by itself (an optional
final newline is allowed) and the form section is the last bundle section.
A marker ending an earlier form section remains source content.
That response marker is removed; the preceding newline is
retained. Inline markers and nonterminal marker lines remain source content.
Do not append commentary after the final form section.

All three paths are validated and complete UTF-8 files staged beside the targets
before replacement begins. Existing file permissions are preserved; new files
use the usual umask-based permissions. Ordinary replacement failures restore previous files and
remove newly installed files. Empty directories created during staging can
remain after failure. An interrupted installation leaves a persistent recovery intent; see below.


Plugin-wide data removal streams only ``id`` and ``plugin_data`` with a
noncaching iterator in batches of 100 database rows. It retains row locks and
whole-snapshot conditional updates inside one transaction: a conflict rolls
back all earlier removals. Model hydration is bounded independently of the
resume inventory; each individual JSON payload still has its own size cost.

Inline control ownership
------------------------

Place each ``badge-editor`` within its owning ``editable-form`` and point
``input-field-id`` at exactly one hidden input inside that component's form.
Repeated fragment IDs in other components are safe; missing, non-hidden or
ambiguous local targets show an error without installing editing handlers.
Each checkbox with ``data-field`` (or a name fallback) updates the matching
hidden input's ``data-field``/name on change and immediately before submit.
Reconnects retire the old listeners before rebinding controls.

Badge drafts and budgets
------------------------

Skills, project and timeline forms share the same badge domain: at most 1,024
strings, each at most 1,024 Unicode code points, with at most 65,536 code points
across the list. Server validation, imports and browser hydration enforce these
limits. Browser hydration validates the complete list before replacing editing
DOM. An invalid/oversized stored list remains unchanged in its hidden field and
shows an error that blocks saving the owning form, so it is never silently
rewritten. Correct that data through a validated editor, or use the editor's
explicit "Clear badges" action to replace it with an empty list and save the
rest of the form. Public display/export includes only a bounded prefix
of valid badges and never rewrites the stored source. Bound form errors retain
the submitted badge payload rather than replacing it with the old list.

Add and Enter commit pending text through the same validation. Saving the owning
form also commits a valid pending badge before HTMX serializes it. Duplicates or
exceeded limits show an inline error and stop submission, retaining the typed
text and existing badges. Correct or clear the pending text and save again.

Plain editable text uses structural line breaks: ``br`` inserts a newline and
block elements such as ``div``, ``p`` and ``li`` separate lines. Blank lines
inside the value survive all native submission paths, and literal angle brackets
remain text. ``data-type="html"`` editors retain their HTML projection.

Streaming plugin responses iterate in the selected resume language. Rebinding
the same response to another supported language updates subsequent iteration
steps and cleanup. File responses keep their original byte stream and use the
latest language for cleanup. Each sync/async iteration step restores the
caller's language before yielding bytes. Exceptions and cancellation also
restore it. Django's synchronous
``response.close()`` and its registered resource closers run in that language.
For early cleanup, async streaming sources must provide the synchronous
``close()`` hook supported by Django's response lifecycle; Django does not call
an async source's ``aclose()`` on response close. Generators still clean up in
their iteration language when exhausted, failed or cancelled during a step.


Recovering interrupted plugin commands
--------------------------------------

Create and remove commands record ``.django-resume-plugin-NAME.intent.json`` in the
project root (the current directory, also when ``templates`` or ``core/plugins``
is a symlink to another tree) before the first installed file changes, while holding all three
writer locks. The intent names the exact targets, SHA-256 hashes and sibling
``.FILENAME.backup-*`` (old) and ``.FILENAME.new-*`` (new) copies. Absence of an
old file is recorded explicitly. For creation, both complete generations survive process
termination, including termination after the final replacement. A subsequent
create or remove refuses the unresolved intent instead of accepting a mixed
bundle. Do not delete the intent or its referenced files.

Both commands check every target against its recorded old bytes or absence
after preparing the intent. They recheck each target immediately before
changing it and refuse files edited or replaced during the check. A conflict
preserves the edit. Before the first file mutation it also retires the intent.
After a mutation starts, the intent and recovery copies remain available.
A removal conflict rolls back the database transaction. During rollback after
other failures, the command checks for unrecognized generations and restores
only files it attempted to change.

Creation also checks each staged file against the intent immediately before
installation, then checks all installed files after syncing their directories.
A generation mismatch keeps the intent and recovery copies for inspection and
explicit recovery.

Intents are per project root. Sharing one symlinked ``templates`` or
``core/plugins`` tree between several projects is not supported for plugin
create/remove: another project cannot see this project's unresolved intent and
could mutate the shared targets before recovery. Resolve every intent before
running these commands from another project that shares the tree.

Stop unrelated editors and run these commands from the same project root,
using the same account, mount and lock directory as the interrupted writer::

    python manage.py recover_plugin NAME --action status
    python manage.py recover_plugin NAME --action restore

``status`` only prints the recorded operation and recovery files, or ``No
interrupted plugin publication`` when no intent exists. The intent is read once,
without following links or blocking, and must be a regular file of at most
131,072 bytes that does not change while it is read; a FIFO, directory, link,
oversized, changing, malformed or excessively nested record is refused with
``Cannot read recovery intent`` and nothing is changed. ``status`` prints the
exact bytes it admitted (also when a recovery copy is missing or fails its
digest check, followed by the validation error); ``restore`` and ``finish``
refuse such an intent. ``restore``
restores all three old files (removing targets that were originally absent).
To install the complete recorded new generation instead, use
``--action finish``. Recovery validates the target set and every copy's digest
before changing files, and holds the same writer locks. It retains authority
copies throughout recovery, so an interrupted recovery can be repeated.
Before each file change and before retiring the intent, recovery checks that
the intent still has the admitted file identity and bytes. A conflict stops
recovery, reports that the intent changed, and leaves the visible intent and
recovery copies for inspection. Earlier file changes may already have completed.
Recovery attempts to sync every affected directory, children before parents,
even if an earlier directory sync fails. It reports the first sync error and
keeps the intent and recovery copies so the same action can be retried. Only
a complete recovery retires the intent and admits new mutations.

Recovery only replaces what the interrupted command owned. Before changing
anything, it requires every installed target to hold one of the two recorded
generations: the old or new bytes, or absence where that generation was
absent. Any mixture of recorded generations (for example after an interrupted
recovery) is accepted in either direction. A target edited, repaired or newly
created after the interruption, or replaced by a directory or other special
file, is a third generation: recovery refuses with ``neither recorded
generation is installed at ...``, names the targets, and keeps the files, the
intent and every recovery copy. A target replaced by a link resolves elsewhere,
so recovery refuses it earlier during target resolution (for example because
it escapes its directory, collides with another target or no longer matches
the recorded target set), equally without changing anything. Each target is checked again, and each staged
copy's digest re-verified, immediately before it is replaced; a change in that
window stops recovery the same way, leaving a recognized mixed state.

To reconcile such a target without losing the change, move or copy the changed
file somewhere outside the plugin tree, then put back the recorded copy that
``status`` lists for it (``old`` or ``new``), or remove the target where that
generation is recorded as ``null``. Repeat ``restore`` or ``finish``, then
reapply your change deliberately. Never delete the intent to skip this check.

Removal records the selected database alias, backend and database name, with
an explicitly unknown outcome. A crash before commit rolls back database data;
a crash after commit leaves deletion committed. Neither file absence nor an
intent proves which happened. Inspect the recorded database with a fresh
connection (and your database backup/audit history) before choosing recovery.
If the removal rolled back, use::

    python manage.py recover_plugin NAME --action restore --database-outcome rolled-back

If removal committed, use::

    python manage.py recover_plugin NAME --action finish --database-outcome committed

These options are the operator's assertion of an independently verified DB
outcome; recovery does not query or modify resume data, and refuses a missing
or mismatched assertion. ``finish`` removes the three files; ``restore`` copies
back their original code. Restoring files alone cannot recover committed data
removal: use a database backup if that operation must be undone. Leave the
intent unresolved if the result is ambiguous. Ordinary successful removal
retires its intent only after its outermost database transaction commits;
invocation inside an existing application transaction is rejected.

Keep the project unavailable while resolving a mixed generation: native locks
serialize cooperating writers, but do not prevent Python/template readers or
unrelated editors from observing intermediate files. Backups and intents may
contain private source; protect the project tree accordingly. Orphan stage or
backup files not referenced by an intent can be inspected and removed after all
writers have stopped. Never remove a referenced recovery copy.


Plugin publication durability
-----------------------------

Create synchronizes every closed staged file and both old/new authority copies
before publication. Removal synchronizes its old authority copies. Both commands
synchronize sibling directory entries and newly created parent directories,
then atomically write and synchronize the intent and its parent before changing
installed files. After replacements/unlinks (and the removal DB commit), they
synchronize every affected directory before retiring the recovery intent.
Intent deletion is also synchronized before recovery copies are collected.
Recovery synchronizes replacement bytes and directories with the same ordering.
This requires filesystem support for file and directory ``fsync``; unsupported
or failed synchronization is reported as an error, never skipped.

A prepublication failure leaves the installed generation unchanged. If the
intent was already visible (for example its directory synchronization failed),
the error reports ``Plugin files unchanged, but recovery intent retained`` with
the intent path; that intent still blocks mutations, so inspect it with
``recover_plugin NAME --action status`` and restore before retrying. For a
removal, no transaction ran yet, so ``--database-outcome rolled-back`` is the
correct assertion for that restore. An ordinary
replacement failure restores and synchronizes the old set. A directory-sync
failure after publication reports ``Plugin files visible but durability
uncertain`` and retains the intent and both recovery generations. It does not
blindly roll files back after a visible publication or a removal DB commit.
For a removal this message adds that the transaction committed, so
``--action finish --database-outcome committed`` applies.
Inspect with ``recover_plugin ... --action status`` and explicitly restore or
finish as above. A failure during intent retirement likewise retains the copies
and attempts to re-establish the visible intent. During recovery this restores
the admitted bytes only if the intent path is still vacant. An ongoing storage
failure may prevent that write, in which case stop writers and preserve every
named copy for manual reconciliation. Cleanup warnings after durable retirement
only name unreferenced leftovers; they do not change the completed operation's
outcome.

These sync boundaries acknowledge the filesystem's durability contract, not a
transaction for readers across three files, nor a replacement for database
backups or reliable storage hardware. A process kill can be reproduced in tests;
power-loss behavior is verified through sync ordering and injected I/O failures.
