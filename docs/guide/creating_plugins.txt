==========================
Tutorial: Creating Plugins
==========================

.. admonition:: Choose your tutorial

   django-resume supports two types of plugins. Choose the tutorial that matches your needs:

   - **Simple Plugins**: Single-form plugins like "About", "Motto", or "Contact Info"
   - **List Plugins**: Multi-item plugins like "Projects", "Certifications", or "Jobs"

Overview
========

Plugins in django-resume are Python classes that define how specific sections
of a resume are displayed and edited. Each plugin handles its own data,
provides forms for editing, and renders content using templates.

Custom plugins are filesystem-based: you add Python modules to your project,
store templates on disk, and register the plugin classes from Python code.
Database-backed plugins are no longer supported.

Plugin Types
============

django-resume provides two base plugin types:

**SimplePlugin**
   For plugins with a single form and straightforward data structure.
   
   Examples: About section, personal motto, contact information, availability status.
   
   **When to use**: When you need to store and display a single piece of content
   that doesn't need to be broken into multiple items.

**ListPlugin**
   For plugins that manage collections of related items.
   
   Examples: Work experience, projects, certifications, education, skills.
   
   **When to use**: When users need to add, edit, and manage multiple related items
   with individual forms and ordering.

Quick Start Recommendations
===========================

**For beginners or simple content**:
   Start with :doc:`creating_simple_plugins` to learn the fundamentals.

**For experienced developers**:
   Jump to :doc:`creating_list_plugins` if you need to manage multiple items.

**Not sure which to choose?**
   Ask yourself: "Will users want to add multiple instances of this content?"
   
   - **Yes** → Use List Plugin
   - **No** → Use Simple Plugin

Supported Custom Plugin Workflow
================================

Custom plugins are added in three parts:

1. Write the plugin class in your Django project.
2. Add the plugin templates under ``templates/django_resume/plugins/...``.
3. Register the plugin class from your app's Python code, usually in
   ``AppConfig.ready()``.

This keeps plugin behavior explicit and version-controlled alongside the rest
of your project code.

Removing filesystem plugins
---------------------------

Run ``python manage.py remove_plugin_by_name NAME`` from your project's root
to remove ``core/plugins/NAME.py``, the plain content/form templates under
``templates/django_resume/plugins/NAME/plain/``, and that plugin's stored data
from every resume. Missing files are allowed. All three paths are validated
before any changes; paths escaping their expected tree or resolving to the
same file are rejected.

The command creates sibling ``.FILENAME.backup-*`` copies before removing
files and uses a database transaction. Resume rows are locked where supported
and checked against their original JSON data before updating. A concurrent
SQLite edit can abort removal with a database conflict; retry the whole command
after that writer finishes. An ordinary file or database failure
rolls back the data change and restores the files. Ctrl+C also triggers
restoration. Cooperating create/remove commands take native ``filelock`` locks
on each resolved target, in sorted order, before backup and hold them through
the database transaction and any rollback. Waiting has a total 10-second budget;
a busy writer raises ``CommandError`` and can be retried. Unrelated plugin
targets remain independent. Lock names are SHA-256 hashes of normalized resolved
target paths in a private per-account directory under Python's OS temporary
directory (``django-resume-plugin-locks-ACCOUNT/*.lock``). On POSIX this directory
must be owned by the current uid with no group/other permissions; symlinks and
non-directories are rejected. Cooperating writers must run as the same account,
share that directory (including the same ``TMPDIR`` configuration), and use the
same canonical path spelling and mount. Separate temp/container namespaces or
alternate case spellings on case-insensitive filesystems are outside this lock
contract. No output directories are created just to remove absent files.

Do not manually delete active lock files; ``filelock`` owns their lifecycle.
Locks are released when their process exits, even if files remain. A busy
writer can be retried after it finishes. If the lock directory is unsafe or
inaccessible, stop all cooperating writers and configure the same private
``TMPDIR`` for every invocation before retrying; do not remove another user's
lock directory or switch namespaces while a writer is active.

This is not a transaction across the filesystem and database: process
termination, unrelated editors (which do not take these locks), or a further
I/O failure during recovery can leave partial results. Stop unrelated editors
and keep a database backup. If restoration
fails, the error lists affected paths and retained backup locations; restore
those files manually before retrying. A backup cleanup warning after success
means the operation completed but the named leftover backup needs removal.
Cleanup logs a bounded warning through
``django_resume.management.commands._file_rollback`` naming leftover paths;
even strict Python warning filters or a failing logging handler cannot replace
the primary error or turn completed publication into failure. Failed
restoration retains the recovery copy.

Installing filesystem plugin bundles
------------------------------------

``python manage.py create_plugin_from_stdin < bundle.txt`` intentionally
replaces existing plugin files. The bundle begins with ``===NAME===`` and must
contain exactly one section for each of ``===NAME.py===``,
``===django_resume/plugins/NAME/plain/content.html===``, and
``===django_resume/plugins/NAME/plain/form.html===``. Names use lowercase
letters, numbers and underscores, starting with a letter. Missing, duplicate,
unknown or malformed sections raise ``CommandError`` before output files are
opened. Generation and stdin installation preserve literal ``---`` in form
text, comments, attributes and scripts. A legacy end-of-response marker is
recognized only when ``---`` occupies the final line by itself (an optional
final newline is allowed) and the form section is the last bundle section.
A marker ending an earlier form section remains source content.
That response marker is removed; the preceding newline is
retained. Inline markers and nonterminal marker lines remain source content.
Do not append commentary after the final form section.

All three paths are validated and complete UTF-8 files staged beside the targets
before replacement begins. Existing file permissions are preserved; new files
use the usual umask-based permissions. Ordinary replacement failures restore previous files and
remove newly installed files. Empty directories created during staging can
remain after failure. The same crash, concurrency and recovery limitations as
removal apply; errors identify retained backups when manual recovery is needed.


Plugin-wide data removal streams only ``id`` and ``plugin_data`` with a
noncaching iterator in batches of 100 database rows. It retains row locks and
whole-snapshot conditional updates inside one transaction: a conflict rolls
back all earlier removals. Model hydration is bounded independently of the
resume inventory; each individual JSON payload still has its own size cost.
